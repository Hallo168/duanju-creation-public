# 偏好蒸馏规范（用户审稿修改 → P 条目的操作规程 · 命令不加载）

> 定位：CLAUDE.md"审稿反馈闭环"的执行细则。用户品味唯一存放处 = `审稿修改经验.md`（P 编号），本文规定怎么往里蒸馏，保证条目精炼、不重复、不含糊。

## 一、什么算"该蒸馏的信号"

- 用户审稿时改了稿（改台词/删戏/换设定）——**每一处都要过蒸馏三问**，不许只改稿不归因
- 用户在对话里的口头纠正（"以后都""这种情况就""别再"句式 = 强信号，必须入库）
- 用户否决了某个方案/前提（如"相亲对象"被否）——否决理由本身就是规则

## 二、蒸馏三问（逐处过，答完才动笔）

1. **个案还是规律？** 只适用于这一处剧情的（如某句台词换个词更顺）= 个案，改稿即止不入库；能想象"下一集换个题材还会遇到同样选择"的 = 规律，入库
2. **提炼到什么高度？** 通用化到"下次换题材还能用"，但保住操作性——条目里必须有"什么情况下、怎么做/不做什么"，纯态度句（"要真实""要接地气"）不合格
3. **用户为什么这么改？** 改动背后的理由必须写进规则。不确定就问用户，**不猜**——猜错的规则比没有规则更毒（04集"回南天"理由记错，靠用户纠正才修正）

## 三、条目格式（一字不差照此写）

```
**P-NN 一句话规则名【可选标记：合规硬线】**
- 改前：`引用户改前原文` → 改后：`引用户改后原文`
- 规则：通用化表述，写清"什么情况下怎么做/不做什么"
- 来源：集号（+阶段：大纲/审稿/分镜/生成）
```

- **必须带改前改后案例**（用户原话优先引用）——案例是规则的证据和歧义消除器，无案例不入库（口头纠正无稿可引时，引用户原话）
- 编号顺延不复用；升格后原编号留索引行（第九节）

## 四、入库四步

1. **查重**：先 Grep 关键词搜 审稿修改经验.md——已有相近条目就**合并强化**（补新案例、必要时改规则表述），不另立新条
2. **归章**：按现有章节（合规/逻辑常理/人物道具/台词/冲突节奏/空间走位/带货/大纲结构）就近归入；都不合适才新开节
3. **双写**：正文条目＋头部检查清单行，同一次操作完成
4. **回检**：新条目和既有条目有没有打架（如"台词要直给" vs "要潜台词"）——有张力就在条目里写清各自适用边界，不留两说

## 五、升格通道（偏好 → 规范）

P 条目满足其一即升格：
- 连续两集都实际用到，且用户没有再修正
- 用户明说"这是铁律/以后必须"
- 条目本质是生成层技术规则而非剧情品味（如 P-25「」符号）——应该活在对应规范文件里

升格动作：本体移入对应规范文件（拿该文件前缀新编号）→ 原 P 条目移到第九节留一行索引（"P-NN → 已升格 T16"）→ 引用它的命令如有直接引用，同步更新

## 六、体检节拍

- 每集审稿完：立即蒸馏（趁上下文还在，隔天必丢细节）
- 每集完结：随知识库"集间五检"（知识库整理规范§六）一起过一遍 P 库——查重、查矛盾、查该升格的
